## Brand tokens
Navy `#1a2236` · section navy `#151d2e` · footer `#111827` · orange `#ea6b14` · text `#f0f4ff`.
Fonts: **Archivo** (headlines on public marketing/content pages), **Bebas Neue** (headings on app chrome, plus all small labels/chips/numerals/buttons/logo everywhere), DM Sans (body). All three are loaded by the single `<link>` in `index.html`, which is **the only font load that reaches every page** — the ~39 per-page `<link>`/`@import` loaders are each a *subset* of it (three disagree about DM Sans weights; one asks for no Bebas at all), so they are harmless only because the superset already arrived, and a selector edit on one page needs no font-loading work. **A face used site-wide belongs in that `<link>`, never in a page's own `<style>`.**

### The display face is a token (2026-10-31)

**The display face is `var(--ff-font-display)`, weight `var(--ff-display-wght)` (700), and nothing in `src/` names a face directly.** Both tokens live in plain `:root` in `main.tsx`. Before this, the face was the literal `'Fraunces', Georgia, serif` hardcoded in **19 places across 12 files** — eleven of them inside stringified `<style>` blocks, three as inline `style={{…}}` objects on Home's `h2`s — so changing it meant 19 edits, and any single miss rendered a page in two display faces with **no error anywhere**. The token makes the next swap one line.

**Archivo replaced Fraunces for a structural reason, not an aesthetic one.** The complaint was that the homepage face read "too cursive", but the real defect was that every band on Home states itself **twice**: the band headline in the display face, and the card titles *inside that same band* in Bebas Neue — with DM Sans body underneath, three unrelated faces per band. A high-contrast serif above condensed Bebas caps read as a collision rather than a hierarchy. Archivo is Bebas's closest relative on Google Fonts (same grotesque skeleton, same tight apertures), so a headline and the card titles under it finally read as one family at two sizes. **If the face changes again, the test is "does it sit above Bebas", not "is it nice".**

**A grotesque at 500 is not a serif at 500**, and this is the part that is easy to get wrong. Fraunces' stroke contrast carried display weight on its own; Archivo needs mass and much tighter tracking, so the display sites are **700** at roughly **-0.028em**. The original ask on the hero h1 had been "less bold" (which is why it was Fraunces 500) — going to 700 is not a reversal of that, because a grotesque at 500 in 3.6rem type reads as under-set *body copy*. Swap the token without revisiting weight and tracking together and every headline looks underset.

**Sub-display sites deliberately keep weight 500**, not the token: `.ff-panel-label` (1.22rem, the hero panel's own heading) and `.ff-about-tagline` (up to 2rem, a pull-quote). At those sizes 700 made them compete with the h1 instead of reading as its subordinate. The weight bump exists to stop a grotesque looking under-set at *display* size; these aren't display size. `.ff-about-tagline` also comes off `letter-spacing: normal` only as far as `-0.012em` — a grotesque set loose at quote size looks accidental, set tight it looks like a heading, and a pull-quote is neither.

**Fraunces is GONE from `index.html`** and from Home's `@import` (which was a strict subset of the `<link>` and only ever blocked Home's own stylesheet while the browser revalidated a request it had already made). Nothing under `src/` renders Fraunces; the remaining mentions are comments recording this history. **If it ever comes back, it comes back in that `<link>` AND in the token together** — one without the other either silently falls back to Arial or silently pays for an unused variable-font download. Archivo is requested as `wght@400..700` with **no `wdth` axis**, because nothing sets `font-stretch` and a second axis roughly doubles the file for no rendered difference.

**The headline face SPLITS BY SURFACE, and the rule is "pages you read vs. pages you operate" (2026-10-10).** The display face applies on the pages someone reads — Home, About, ForContractors, ServicesIndex, ServiceLanding, AreaLanding, Blog, BlogPost, ContractorGuide, UserAgreement, PrivacyPolicy, ProtectionPromise. **Bebas Neue stays the heading face on everything operated**: all three dashboards, both onboarding flows, Login / UpdatePassword / AuthCallback, PickPro, GetQuote (a public page, but a *form*), both success screens, ProfileCompleteCelebration, FreddyRewind. A dashboard `h1` is dense UI chrome sitting inches from twenty controls, not a headline, and a display serif there reads as a different product. `ContractorProfile.tsx` is deliberately left on Bebas too: it is public, but it is a **data record** rather than editorial content, and four of its five Bebas sites are labels or numerals that would have to stay — converting the fifth alone would break that one page's internal consistency.

**Bebas was demoted, not removed.** It keeps every small label, chip, badge, step counter, stat numeral, CTA/button and the logo, on *all* surfaces — including inside the display-face pages. So a display-face page still carries Bebas on `.ff-service-label`, `.ff-how-step`, `.ff-stat-num`, `.ff-ba-label`, `.ab-cta` / `.fc-cta`, and every `h3` card title.

Three mechanics, each of which bites differently:

- **A selector naming `h3` must be SPLIT, never swapped.** `h1,h2,h3{font-family:'Bebas Neue',…;letter-spacing:.0Xem}` becomes `h1,h2{font-family:var(--ff-font-display);font-weight:var(--ff-display-wght);letter-spacing:-.015em}` **plus a standalone `h3` rule carrying the original tracking verbatim** — h3s are card titles and stay Bebas. **The tracking value is NOT uniform across files** (`.06em` on the legal/content pages, `.05em` on ServicesIndex / ServiceLanding / both AreaLanding blocks, `.04em` on `.fc-faq h3`); copy it per file rather than assuming.
- **`About.tsx` and `ForContractors.tsx` use an element-scoped override instead**, because `.ab-h` / `.fc-h` are reused on h3s and on a numeral. The class rule stays Bebas and `h1.ab-h,h2.ab-h{…;letter-spacing:normal}` is appended — element+class is 0,1,1 and beats the bare class's 0,1,0. **The `letter-spacing:normal` is mandatory**, or the h1 inherits the class's Bebas tracking.
- **`Home.tsx` tracks tighter than every other page: `-0.028em` on its display headings against `-.015em` on the sub-pages.** Home's headings run 2.5–5rem where a sub-page `h1` is ~1.5–2.9rem, and tracking has to tighten as size rises or a grotesque opens up visibly. The two numbers are **not** a drift to reconcile — reconciling them would under-track Home or over-track the sub-pages. Sub-display sites on Home (`.ff-panel-label` at `-0.01em`, `.ff-about-tagline` at `-0.012em`) sit closer to normal on purpose. Home also has **no bare element heading selectors at all** — every heading is a named `.ff-*` rule or an inline style object — so neither mechanic above applies and each site is judged individually.

**`line-height` must rise off 1.0 when a display heading changes face.** Bebas is condensed with all-caps metrics and effectively no descenders, so `line-height: 1` is safe; both Fraunces and Archivo have real descenders and will overlap on a two-line wrap at 5rem. `.ff-about-headline` went `1` → `1.05` under Fraunces and sits at `1.02` under Archivo, with the hero at `1.04` — Archivo's descenders are shallower, so the values could tighten, but **the floor is 1.0 and they never go below it**. This is a mechanical consequence of the face, not a design preference.

**Do not reach for `font-variation-settings` on the display face** — see the comment on `.ff-h1` in `Home.tsx`: setting `wght` there overrides the `font-weight` declaration outright, which now means overriding `--ff-display-wght` and quietly decoupling that one site from the token. Archivo is loaded as `wght@400..700` with no other axis, so there is nothing else there to reach for anyway.

**There is now ONE easing scale, for the same reason there is one shadow scale — `--ff-ease-out` / `--ff-ease-in-out` / `--ff-ease-drawer` in `main.tsx` (2026-10-10).** `cubic-bezier(0.22, 0.61, 0.36, 1)` had been hand-pasted into three separate rules with no shared token, so "our enter curve" had three copies and no name — and the stock `ease` keyword appeared *alongside* it in rules that are part of the same gesture (`.ff-fade` eased differently from the `.ff-enter` it sits beside). Values are `0.23, 1, 0.32, 1` (out), `0.77, 0, 0.175, 1` (in-out) and `0.32, 0.72, 0, 1` (drawer).

**They live in the plain `:root` block and are DELIBERATELY NOT inside `.ff-on-dark`.** Easing is a timing function, not a colour, so it is theme-independent — the seven colour aliases need literal duplicates in that class only because a `var()` inside a custom-property *declaration* substitutes where it is declared; a bezier literal has nothing to substitute. Adding them to the scope class would be two copies of a value that must agree, for no benefit.

**The scale gained a fourth member on 2026-11-08: `--ff-ease-spring: cubic-bezier(0.34, 1.56, 0.64, 1)`.** The other three all land *at* their target; this one **overshoots past 1 and settles back**, which is what makes a dialog read as a physical object arriving rather than a box fading in. Use it for a **one-shot entrance** — `.ffu-modal-in`, a sheet rising, a chip appearing. **Do not use it on a `transition` for a reversible state** (hover, open/close, a press): a curve that overshoots looks like a bug when the gesture reverses mid-flight, and the press already has its own asymmetric handling below. There is still exactly one of each curve; a fifth needs a reason in this file.

## The Apple material language (2026-11-08)

Added when the owner asked for the site to feel "more Apple-ish". **Scope was decided explicitly and the exclusion is as binding as the inclusion:** *feel and materials* — translucency, layered shadows, true hairlines, springy entrances, generous targets, focus rings, bottom-sheet dialogs. **The palette and the type rules were deliberately left alone.** Navy/orange stays, and the Bebas-on-operated-surfaces split stays. "Apple-ish" here means Apple's *material* vocabulary applied to this brand, never Apple's brand.

Four token families, in `main.tsx`. **Which block each one lives in is the whole subtlety**, and it follows the same rule the colour aliases follow:

| token | `:root` (dark) | light override | `.ff-on-dark` | why |
|---|---|---|---|---|
| `--ff-glass` | `rgba(26,34,54,0.72)` | `rgba(233,238,248,0.76)` | **literal** `rgba(26,34,54,0.72)` | a translucent **ground** — theme-dependent, so it is exactly the alias trap |
| `--ff-glass-blur` | `saturate(180%) blur(20px)` | — | — | a filter value, not a colour; theme-independent |
| `--ff-hair-w` | `0.5px` | — | — | a width, not a colour |
| `--ff-mat-1/2/3` | black-based | slate-based, much lighter | **literal**, black-based | a shadow on navy and a shadow on off-white are different shadows, not the same shadow at a different opacity |

**`--ff-glass` is an opaque-*enough* colour under the blur, not a near-transparent one.** A real translucent bar over arbitrary page content is unreadable. 0.72–0.76 plus `saturate(180%)` is the combination that reads as frosted glass while text on it stays legible — the saturation boost is what stops the blur looking like grey mud, and it is the half of the recipe people drop.

**The hairline is `0.5px`, and that is not a typo.** On a 2×/3× display a `1px` border is two or three device pixels and reads as a drawn line; `0.5px` resolves to one device pixel and reads as an *edge*. On a 1× display the browser rounds it up to 1px, so there is no "invisible border" failure mode — which is why this is a plain value and not a media query.

**The shadow scale is layered, 1/2/3 = resting / raised / floating**, each a *stack* of shadows rather than one. A single large soft shadow reads as a glow; a tight contact shadow plus a wide ambient one reads as an object above a surface. `--ff-mat-3` carries three layers because a floating dialog needs the contact shadow, the ambient spread, *and* a very wide low-opacity layer that separates it from the scrim.

**`--ff-accent-rgb` (`234,107,20` dark / `214,95,16` light) is the fifth addition, and it is a migration token.** It exists so `rgba(234,107,20, A)` could become `rgba(var(--ff-accent-rgb), A)` **with the alpha preserved** — the tree had 15 distinct alphas and some are load-bearing (the photo-pulse keyframe animates `.55 → 0`), so folding them onto `--ff-accent-soft` (0.12) and `--ff-accent-line` (0.32) would have been a visual redesign disguised as a token migration. **Reach for `-soft` / `-line` first** when you want the standard tint or the standard hairline; reach for `--ff-accent-rgb` only when the alpha is genuinely something else. And **`-soft` and `-line` must stay spelled out as literals** — rewriting them in terms of `--ff-accent-rgb` is the alias trap, and `tools/check_tokens.py` now fails on it. Full migration story in `docs/ux-laws.md`.

**The shared primitives in `src/components/ui/uiStyles.ts` are where the materials actually land**, so a surface gets them by using a primitive rather than by reading this file: `.ffu-glass` (the frosted ground), `.ffu-scrim` + `.ffu-modal` + `.ffu-grab` (the dialog), and the `:focus-visible` block. **`.ffu-modal` becomes a bottom sheet below 560px** — `.ffu-scrim { align-items: flex-end; padding: 0 }` and the modal squares its bottom corners and grows a `.ffu-grab` handle. That breakpoint is a phone/not-phone split, not a design grid column, which is why it is 560 and not one of the layout breakpoints. `ConfirmDialog` is the reference implementation.

**The 19 hand-rolled modals that predated it: 15 moved over on 2026-11-08, 4 remain, and the 4 are shape constraints rather than a backlog.** Converting one is mechanical — delete the overlay and card style objects, add `className="ffu-scrim"` / `"ffu-modal"` — and the payoff is bigger than it looks, because each conversion deletes four or five hand-chosen spacing literals along with the card, which is why the Proximity ratchet fell 1503 → 1486 → 1481 → 1478 across this pass with no spacing migration at all. Two of those three falls are modal conversions — 1503 → 1486 from the first 13, 1481 → 1478 from the last two — and the middle one is `<PageTitle>` doing the same thing to three read pages, so read the chain as one mechanism rather than as modals alone (see `docs/ux-laws.md`). Converted: `DeleteAccount`, `CompletionThanksModal`, `ReportProblem`, `AdminMessageModal`, `VerifyCodeModal`, `FileClaimModal`, `ChatTimePrompt`, `GoogleReviewModal`, `ProfileCompletionModal`, `RespondToClaim`, `RequestHelpModal`, `ReferralShareModal`, `SettingsModal`, `ProfileCompleteCelebration`, `FreddyRewind`.

**`.ffu-modal-flush` came out of that pass and exists so a dialog does not have to re-roll the card to escape its padding.** Some bodies must reach the card's edge — a full-bleed image, a list whose rows carry their own separators, a scrolling region that would otherwise show a padded gutter beside its scrollbar. The wrong fix is a negative margin on the child, which breaks the moment the card's padding changes; the wrong fix is a second card class, which is the drift this whole pass is undoing. `-flush` zeroes the padding on the card and hands it to the sections that want it.

**The 4 that remain cannot use `.ffu-modal` as written**, because the primitive is a centred card with a max-width that becomes a bottom sheet below 560px, and these are not that shape: `OnboardingVideo`'s panel is `55vw / max-width 1200px` because it holds a video and a narrow card would letterbox it to nothing; `OverhaulNotice` is two layers at once, a bottom bar (`.ff-ovl`) plus a separate full-inset panel (`.ff-ovlp-back`), both built as classes inside an injected string rather than as style objects; and `BidChat` and `JobChat` are chat panels rather than cards — `BidChat` sits at `align-items: flex-end` at **every** width, not only below 560, which is the opposite of the primitive's breakpoint behaviour. **Converting any of those four means changing what they look like, so they are design decisions, not cleanup.**

The last two conversions — `ProfileCompleteCelebration` and `FreddyRewind` — were done later the same day and each taught something the first 13 had not, because both have a reason not to take the primitive's own colours.

**`ProfileCompleteCelebration` is a PARTIAL conversion, and the three things it declines are each declined for a mechanical reason, not a cosmetic one.** The card is deliberately hand-painted dark in both themes (its `#f0f4ff` text and navy gradient are literals on purpose), so the gradient ground stays as an inline override of `--ff-glass`. Dropped rather than carried over: its **accent card border**, because an inline `border` **shorthand** beats the sheet's `border-left: 0; border-right: 0; border-bottom: 0` and the bottom sheet would have kept four borders and stopped reading as attached to the device edge — and because it was the fourth orange thing on one screen where the rule is one; and **`ffPop`, its bespoke `.85 → 1.03 → 1` entrance**, because an inline `animation` beats `ffu-sheet-in` too and would have left a card scaling up from the bottom edge instead of rising from it (`ffu-modal-in` springs from `.96`, so the overshoot is not lost). It also gets **no `.ffu-grab`**, and that is a decision: the grabber is the signal "this panel is dismissible", the dismiss it promises is the scrim tap, and this scrim has no `onClick` — a celebration exits through one of its two named buttons. **A grabber on a non-dismissible sheet is a lie about the affordance.**

Its confetti `<canvas>` stays a **sibling** of the card inside the scrim, so it is clipped to the scrim's padding box rather than the viewport — a `backdrop-filter` ancestor becomes the containing block for a `position: fixed` descendant. That is **pre-existing** (the hand-rolled overlay blurred too, at `padding: 1.5rem`) and the primitive *improves* it: the sheet branch takes padding to 0 below 560px, so on a phone the confetti now reaches all four edges. Hoisting it out of the scrim to fix the desktop inset was considered and rejected — it would need a `z-index` above the scrim, which would rain confetti over the card's text instead of behind it.

**`FreddyRewind` takes the primitive plus `.ff-on-dark.ff-anchor`, and that pair fixed a live light-mode bug the conversion exposed.** Its contents are all light-on-dark literals (`#f0f4ff` share card, `rgba(190,205,235,.75)` failure copy) while its ground was `var(--ff-bg)` — off-white in light mode. **A subtree painted in light-on-dark literals cannot follow the theme, so its ground must not either**, and one class beats re-tinting a dozen values. Its close × also moved to `.ffu-iconbtn`: a bare glyph button is ~14px wide, and the `(pointer: coarse)` block floors `min-height` on a `button` but not width, so the live target was a tall sliver.

The test for a *new* dialog is the reverse of all this: use the primitive unless you can name which shape constraint stops you.

### The frosted-surface contract: prefix, ground, isolation (2026-11-08)

Written later the same day as the material pass above, after an `apple-design` re-audit of the surfaces the first pass had not touched. **All three obligations existed as prose before this; all three were being broken, and each failed in a way that is invisible from the machine the code was written on.**

**(a) `-webkit-backdrop-filter` goes FIRST, before the unprefixed property.** iOS Safari reads only the prefixed form through 15.x. Omit it and the surface simply renders as its flat background — no error, no console warning, and on a Mac the unprefixed property works so nothing looks wrong. `main.tsx:166` has carried this rule since the tokens landed and **four of the eight paint sites in `src/` broke it anyway**: `Home.tsx`'s three before/after carousel chips (`.ff-ba-label`, `.ff-ba-badge`, `.ff-ba-vbtn`) and `JobChat`'s panel scrim.

**What hid it is worth more than the bug.** Both blanket *kill* rules — the reduced-transparency and increase-contrast blocks — were correctly prefixed. So the override worked on iOS and the thing it overrode did not, meaning the only platform where the frost was missing was also the platform where turning the preference on correctly removed a frost that had never been drawn. **A correctly-written override makes a broken base invisible.** The audit had named *one* site in `Home.tsx` from an earlier note; a full-tree grep found three. Grep the tree, don't trust the note — the same rule this repo already applies to documented checks and to the deployed copy of an edge function.

Now **check (7)** in `check_ux.py`, matching both spellings (`backdrop-filter:` in CSS, `backdropFilter:` in a style object) with fixed-width lookbehinds that exclude the prefixed forms, and pairing them within a 200-character look-back **per site**. The per-site window is the point: a file with three prefixed and three unprefixed declarations satisfies any per-file count while pairing none of them.

**(b) The ground carries legibility by itself. The blur is enhancement.** `--ff-glass` is 0.72/0.76 and **0.7 is the floor**. `.ff-ovl` — the overhaul notice bar — was a `rgba(accent, .16) → rgba(accent, .08)` gradient and nothing else, which is a transparent smear with text on it. The fix layers the tint *over* the token rather than instead of it: `background` accepts a list, so `linear-gradient(…), var(--ff-glass)` keeps the orange identity and gains a ground. `JobChat`'s scrim went `.6 → .72` for the same reason.

**This is the reduced-transparency rule reached from the other end, and noticing that is what makes it a rule rather than two fixes.** That block requires a frosted surface to stay legible when the blur is *killed*. The prefix bug means a frosted surface must also stay legible when the blur **never arrives**. Same requirement, two causes, and an alpha at or above 0.7 answers both at once — which is why the floor is a number and not a judgement.

**(c) `isolation: isolate` on every one of them.** `backdrop-filter` samples everything painted below it in the same stacking context, and makes the element a containing block for `position: fixed` descendants (the reason `ProfileCompleteCelebration`'s confetti canvas is clipped to the scrim — see above). `.ffu-scrim` and `.ffu-ptitle-bar` were missing it. **They were missing it because they were written separately, not because anyone decided they were fine**, which is the only interesting thing about it: with four sites in one file and two of them answered, "does this one need it?" was a live per-site question. All four carry it now, so it isn't one.

### The bottom edge of the phone (2026-11-08)

**`env(safe-area-inset-bottom)` appeared exactly TWICE in all of `src/`, both inside `.ffu-modal`'s bottom-sheet branch.** Every other bottom-fixed surface put its last control under the iPhone home indicator, where a tap is a system gesture rather than a tap: `CookieConsent` (bar and its detail panel), `FinishSignupBanner`, `ChatWidget` (bubble and panel), `OverhaulNotice`, and `DashboardSidebar`'s mobile nav drawer. The dialog primitive having answered it is exactly why nobody found the rest — the one surface anybody tested on a phone was the one surface that was right.

**Two shapes, and which one a surface is decides where the inset goes. This is not a style preference.**

| shape | inset goes on | why the other way is wrong |
|---|---|---|
| **strip** — full-bleed bar or painted panel pinned at `bottom: 0` | **`padding`** | lifting it with `bottom` slides the paint up and leaves a transparent band of page content showing underneath it, at the very edge of the screen |
| **floater** — detached, already standing off the edge (the chat bubble) | **`bottom`** | it has no paint spanning the edge to leave a gap in; padding would just inflate the button |

**A full-height drawer is a strip.** `DashboardSidebar`'s nav drawer is `position: fixed; top: var(…); bottom: 0` with its own `--ff-surface` paint, so the inset goes on the scroller's bottom padding. That one was found by **measuring check (8)'s population before writing the check**, not by the audit — which is the argument for running a candidate matcher over the tree before deciding what it should say.

**⚠️ Never a sum where a measured height is involved.** `--ff-fsb-h` is `FinishSignupBanner`'s real `offsetHeight`, published on `:root` — the `--ff-topnav-h` pattern. Once the banner answers its own inset, that measured height *includes* the inset, so a consumer writing `calc(X + var(--ff-fsb-h) + env(safe-area-inset-bottom, 0px))` double-counts and leaves a ~34px hole under the chat panel whenever the banner is up. The correct form is:

```
calc(X + max(var(--ff-fsb-h, 0px), env(safe-area-inset-bottom, 0px)))
```

`max()` because the two cases are mutually exclusive, not additive: either the banner is up and its height already covers the indicator, or it isn't and the raw inset applies. **Measuring rather than declaring is what makes this work at all** — the inset is answered once, at the bar, and every consumer inherits the answer.

**Check (8) would have been RED ON ARRIVAL with two findings**, which this repo forbids ("a gate that cries wolf is a gate someone learns to skip"). Both were read rather than the check weakened. `DashboardSidebar` was a real defect and was fixed. `NotificationBell.tsx:209` sets `bottom: window.innerHeight - r.top + gap` from `positionDropdown()` — a computed anchor measured against the bell, for the case where the dropdown opens upward — so the inset belongs to the measurement and not to the declaration. **Excluding computed values is principled rather than convenient**, and the checker's docstring says so in those terms, because the next person to hit a red check (8) will reach for the same exclusion and deserves to know which half of it was earned.

### The three display preferences (2026-11-08)

**An OS expresses three independent display preferences, and until this was written the site answered exactly one of them.** `prefers-reduced-motion` was handled in 13 places; `prefers-reduced-transparency` and `prefers-contrast` appeared **zero** times in all of `src/` — on the same day the material pass above put `--ff-glass` / `--ff-glass-blur` onto four primitives and left four hand-rolled blurs in `Home.tsx`. So the gap was *opened by* the Apple work rather than inherited from before it, which is the useful thing to notice: a pass that adds a material has to answer the preference that switches that material off, in the same pass, or nobody will ever find it. Nothing throws, nothing looks wrong, and it is invisible on any machine that does not have the preference turned on.

**None of the three substitutes for another, and that is why one of them being present made the other two look handled.** Reducing motion does nothing for a user who cannot read text through a blur. Removing blur does nothing for a user who cannot see a `0.5px` hairline. They are three different complaints about three different properties.

The answer is in three places, and the split is the same one the tokens follow:

| where | what it does | why there |
|---|---|---|
| `main.tsx`, two new `@media` blocks | kills **every** `backdrop-filter` in the document with `*, *::before, *::after { … !important }`, sets `--ff-glass-blur: none`, and under `prefers-contrast` doubles `--ff-hair-w` to `1px` | it is the only rule that cannot be out-specified by an inline style or a per-page `<style>` block — the same reasoning as the reduced-motion blanket beside it and the 16px font floor in the `(pointer: coarse)` block |
| `uiStyles.ts`, two new `@media` blocks | gives `.ffu-glass` / `.ffu-modal` / `.ffu-ptitle-bar` an **opaque ground** (`--ff-surface`), takes `.ffu-scrim` to `.92`, and under `prefers-contrast` sets the modal border and the title-bar rule to `--ff-text` | naming the surfaces by **class** means the ground can be an ordinary theme token that resolves at *use* time — correct in both themes by construction, with nothing duplicated |
| `Home.tsx` and `OverhaulNotice.tsx` | their own `@media` rules for the five surfaces that write a **literal** blur rather than reading the token | `.ff-ba-label` / `-badge` / `-vbtn` sit directly on a before/after **photo**, the worst possible backdrop for a translucent label, and `.ff-hero-panel`'s ground is `0.045` alpha |

**Why the kill is a blanket and the grounds are not.** Four of the eight `backdrop-filter` sites in `src/` write a literal blur, so setting `--ff-glass-blur: none` alone would have missed half the frosted surfaces on the busiest page — hence the universal selector. The *grounds* could not be done the same way: `--ff-glass` is theme-dependent and already spelled as a literal in three palette blocks, so neutralising it from a media query in `main.tsx` would have meant writing the navy and the off-white a fourth and fifth time. Two more hand-maintained copies of the exact value the literal rule already makes someone maintain is a worse outcome than two small blocks living next to the classes they describe.

**This is what finally makes "the surface must stay legible with the blur removed" mechanical rather than aspirational.** That rule shipped with the glass tokens and the `0.72` alpha was chosen for it — but it was a *claim* about 0.72 being enough, tested by eye. Under Reduce Transparency the requirement is no longer "enough", it is "opaque", and the user asked for that explicitly. **Nobody may lower these to get the effect back on their own machine.**

**Two judgement calls worth keeping, because both went against the obvious answer.** `.ffu-scrim` goes to `.92`, **not** solid: a completely opaque scrim stops reading as a layer over the page and starts reading as a *navigation* — the dialog looks like a new screen and the user loses the one thing the scrim exists to tell them, which is that there is something behind it to go back to. And `OverhaulNotice`'s bar **keeps its orange gradient** with an opaque layer painted *under* it (`background` accepts a list, so `linear-gradient(…), var(--ff-bg)`) rather than being replaced with a flat token; the flat token was less code and would have thrown away the only thing making that bar read as a notice rather than as a toolbar.

**It is checked, as check (5) in `tools/check_ux.py`, and it is an absolute rather than a ratchet** — three queries, all three present, a reachable green state, so the usual reason for a ratchet does not apply. Note honestly what it *cannot* see: whether each frosted surface's ground is opaque enough once the blur is gone is an alpha read against an unknown backdrop, and no regex decides it. The check guards against the blocks being deleted or a fourth preference being answered nowhere. **A new translucent surface needs a line in one of these blocks, and that part stays a human obligation.**

### The hairline law and its ratchet (2026-11-08)

`--ff-hair-w` shipped with the material tokens above and then **4 things in all of `src/` used it, against 576 hand-written `1px solid` borders.** That is the same failure the orange token and the spacing scale had: a token exists, the law it encodes is written down, and the call sites never move — so the law is true of the stylesheet and false of the product.

**The argument is per-device-pixel, not aesthetic.** On a 2× screen a `1px` CSS border is two device pixels; on a 3× phone it is three. Three device pixels is what a *drawn line* looks like — it has weight, it separates two regions as equals, and a card made of them reads as a table. One device pixel reads as an **edge**: the thing that tells you where a surface stops without competing with the content on it. `0.5px` is how you ask for one device pixel, and on a 1× display the browser rounds it up, so there is no invisible-border failure mode and no media query is needed.

**The rule that decides whether a given border converts: a SEPARATOR gets thinner, a SIGNAL does not.** A hairline between two rows, a card's own outline, a panel's bottom edge — all separators, all `--ff-hair-w`. A border that is *saying something* — the accent ring on a selected option, the red edge on a validation error, the orange outline on the one thing you are meant to press — is a signal, and halving its weight is halving the signal. Those stay `1px`. This is the same distinction Von Restorff makes about colour, applied to width.

`tools/migrate_hairlines.py` converted **333 borders across 70 files**; the token now has **339 uses** in `src/`, the handful of extras being hand-written into the primitives in the same pass (so don't read 339 as 4 + 333 and go looking for the missing two). It only rewrites a border whose colour is one of three **named neutrals** (`var(--ff-hair)`, `var(--ff-card-border)`, `rgba(var(--ff-fg), A)`) — which is how "separator vs signal" became mechanical instead of a judgement call per site. Note the migration is safe in a shorthand because **`var()` substitution precedes shorthand parsing**, so `border: var(--ff-hair-w) solid var(--ff-hair)` is valid CSS; the failure mode is an *undefined* variable, which invalidates the whole declaration and makes the border vanish — hence the carve-out for standalone HTML documents (the receipt string has no `:root` to resolve against).

**It is ratcheted as check (6) in `tools/check_ux.py`, `HAIRLINE_BASELINE = 21`, and the two scoping decisions are the interesting part.** It counts **only** the three named neutrals, so a legitimate new accent or state border can never make it red — if it counted all `1px solid` it would rise every time somebody correctly marked something as needing attention, and *a gate that cries wolf is a gate someone learns to skip*. And the floor of **21 is measured, not estimated**: it is exactly `migrate_hairlines.py`'s refusal list, every one a **mixed ternary** where the two branches disagree about whether the border is a signal —

```
border: on ? "1px solid var(--ff-c10)" : "1px solid rgba(var(--ff-fg), .12)"
```

— and halving only the neutral branch would make a row of chips shift by half a pixel as the selection moves. That makes this the tightest of the three ratchets: unlike orange (4 permanent hazard classes) and spacing (hundreds of plausible near-misses), **21 is a list of 21 known lines**, and a rise here means a new neutral border was typed as `1px` rather than drift.

### The tap-target floor has two axes (2026-11-08)

The `@media (pointer: coarse)` block raises `min-height` to 48px on every `button`, and that block had been read for months as "touch targets are handled". **It is one axis.** `min-height` says nothing about width, so a control whose content is narrow — an icon, a glyph, a chevron — passed the floor as a **tall sliver**: `FreddyRewind`'s close × was about 14px wide and 48px tall, and Home's two carousel arrows were declared `30px` square and rendered as a **30×48 pill**.

**The arrows are the clearer lesson, because `height: 30px` never had a say.** `min-height` beats `height` outright — they are *different properties*, not competing selectors, so specificity never enters it and nothing in the file looked wrong. A component can therefore be mis-sized by a rule two files away that it appears to override.

Both fixes set the missing axis explicitly, and **they deliberately land on different numbers**: `.ffu-iconbtn` goes to `48px` square (it is the generic icon button, and 48 is what the floor already promised); the carousel arrows go to **44**, because `.ff-ba-knob` beside them is already 44 and 48 would make the arrows the largest circles in a component whose primary control is the knob — and two stacked 48px circles eat ~53% of the image height on a 360px phone, where the image *is* the content. The 44 is restated on the class so it outranks the element-level 48 (a class beats a type selector). **The published minimum is a floor, not a target; the local answer is the one that keeps the component's own hierarchy intact.**

### One separator per chrome stack (2026-11-08)

When a `PageTitle` bar is stuck it parks directly under the lifted nav, and both carry a bottom hairline plus a shadow — so the user sees **two parallel lines 4px apart**, which reads as a rendering fault rather than as structure. `PageTitle` puts `ff-ptitle-stuck` on `<html>` while any bar is stuck; `main.tsx` uses it to take the nav's `border-bottom-color` to `transparent` and its `box-shadow` to `none`, leaving the title bar's own border as **the single separator for the pair**.

Two placement decisions, both about ownership. The **class comes from `PageTitle`** because it owns the stuck state and is the only thing that knows; the **rule lives in `main.tsx`** beside the other two nav-border rules, because every decision about this nav's bottom edge belongs in one place. And it is scoped to `.ff-nav-lifted` — unlifted there is no border or shadow to suppress, and scoping keeps the selector from claiming to do something it does not.

Generalised: **two stacked pieces of fixed chrome share one separator, and the lower one owns it.** The lower edge is the one adjacent to the content, so it is the one that is actually doing the separating.

### The collapsing large title (2026-11-08)

The last piece of the material vocabulary, and the one with real mechanics behind it: a long reading page shows its title at full display size at the top, and once that title scrolls past the nav a compact frosted bar takes over naming what you are reading. `src/components/ui/PageTitle.tsx`, mounted on `UserAgreement`, `PrivacyPolicy` and `ProtectionPromise`.

**⚠️ It is for pages you READ, not pages you operate.** It tracks `h1`s, never `h2`s, and the dashboards have one `h1` and a scroll made of panels rather than of prose — mounting it there would pin a bar naming a page the user is already looking at. If a dashboard section needs a sticky header it needs a *section* header, which is a different component.

**`--ff-topnav-h` is MEASURED, not declared, and that is the fix rather than an optimisation.** The bar has to sit exactly under the nav, and the nav's height depends on wrapping, on the light-mode peek prompt and on the FinishSignupBanner. Three different hardcoded answers to "how tall is the nav" already existed in `src/` and they disagreed. `TopNav` now carries a `ResizeObserver` that writes its own measured height to `--ff-topnav-h` on `documentElement`; the `4.25rem` in `:root` is a **first-paint fallback only**. **Write px there, never rem** — the observer reports px, and a rem value written into a token read by `top:` would be scaled twice once `--ff-font-scale` is involved.

**The handoff rule is the correctness argument, and it is asymmetric on purpose.** A page can publish two documents under two `h1`s (the User Agreement does, and both halves contain a `14. Limitation of Liability`), so "stuck" means *my title is above the line AND the next one is not yet*. `PageTitle` finds its successor by `indexOf` on a live `document.querySelectorAll` of the title class — reading the DOM, so an `h1` left bare on such a page is simply not in the sequence and the bar will confidently name the wrong document. **The 8px hysteresis is on the element's OWN edge only; the handoff edge is an exact comparison.** That is not sloppiness: the successor bar sticks on an un-hysteretic test, because from its point of view that edge is its *entrance*. Put a dead band on the handoff too and the two tests disagree for 8px — widen it one way and neither bar is mounted through the gap, widen it the other and **both** are, stacked at the same `top`. Exact on both sides means they swap in the same frame off the same number.

**Set `--ffu-ptitle-w` to the page's own column width** when you mount it. The bar is `position: fixed`, so without it the bar's text starts at the window edge while the prose it belongs to starts centred in an 800px column, and the bar reads as browser chrome rather than as part of the page. The sheet defaults to 860px; all three current mounts override it to 800px. `compact` exists for titles that will not survive one 44px line on a phone — it is a **label**, not a truncation ("Contractor Terms", not "Contractor Professi…").

**One hazard, and it was fixed at the mechanism rather than at the call sites (2026-11-08).** `Ic` used to render `stroke={color}` — an **SVG presentation attribute**, where `var()` support is uneven enough that `color="var(--ff-c10)"` could resolve to nothing and draw an **invisible icon**. That one component accounted for **68 of the 78 orange literals** the token migration refused, so the fix was to change `Ic`, not to annotate 68 sites: it now renders the constant `stroke="currentColor"` — the one value universally supported in a presentation attribute *and* deferring to CSS — and turns the caller's `color` into a real CSS `color` declaration in the inline style, where `var()` works. Two details are load-bearing: `...style` is spread **after** the colour, so a caller who sets `style={{ color }}` still wins; and `color` now defaults to **undefined** rather than to a literal, so an unstyled icon inherits from its parent instead of forcing a hex.

**The hazard survives for a raw `<svg>`.** Hand-written SVG in a page still carries `stroke="…"` / `fill="…"` as attributes, and a token handed to one of those is still invisible. `fill` and `stroke` are also real CSS properties on SVG elements, so the fix there is to move the value into the style object. `Home.tsx:1279-1281` shows both halves in three lines. This is why the orange ratchet's irreducible floor is raw-SVG attributes rather than `Ic` calls.

**There is now ONE spacing / radius / height scale too, in the plain `:root` block of `main.tsx` (2026-10-30).** `--ff-s1..s10` (4/8/12/16/20/24/32/40px), `--ff-r1..r4` (10/14/18/26px), `--ff-h-row` 48px, `--ff-h-ctl` 44px, and `--ff-gut` 40px. **There WAS a `--ff-h-nav: 42px` in this list and it is gone (2026-11-08)** — grep found exactly one hit in the whole repo, its own declaration. It was deleted rather than left because `--ff-h-nav` and the live `--ff-topnav-h` are one transposition apart, and a dead token that close to a real one is the setup for silently reading the wrong number. If a sidebar nav item ever needs a token it can have `--ff-h-navitem`. Added for the same reason as the easing scale: the three dashboards were each written with ad-hoc `rem` values, so "the gap between two rows" and "the radius of a card" had three slightly different answers and a shared primitive could not be written without picking one arbitrarily. These are what `src/components/ui/` resolves against, and **nothing in that folder hard-codes a value** — that is what lets `<Pass>` re-theme from one prop.

**They are geometry, not colour, so like the easing and shadow scales they are DELIBERATELY NOT duplicated inside `.ff-on-dark`.** A `px` literal has nothing to substitute, so the declaration-site trap below cannot reach them, and a second copy would only be a second thing to keep in agreement. The literal-parity requirement stays confined to the seven colour aliases.

**`--ff-gut` is one token on purpose.** A row's icon column width, the left inset of the hairline separator under it, and the hanging indent of any text that must line up with that column are all the same 40px — spelled as three numbers they drift, and a hairline that disagrees with the column above it by 2px is the kind of flaw that reads as sloppiness without anyone being able to name it. `44px` for `--ff-h-ctl` is not a design choice either: it is the published MINIMUM thumb target, and it is what a control measures **on a mouse-driven desktop**. The `@media (pointer: coarse)` block further down the same stylesheet raises the floor to **48px** (2026-11-08) so that on a phone a control and a row (`--ff-h-row`, already 48) are the same height. **The two numbers disagreeing on desktop is deliberate** — a 48px button under a mouse reads as oversized, and nothing on desktop is hit with a thumb. Don't "fix" it by setting `--ff-h-ctl` to 48; the floor is a `min-height`, so anything already taller is untouched either way.

**`ff-enter` and `ff-enter-b` still have separate `@keyframes` names, and token-izing the easing did not change that.** They are byte-identical twins on purpose: swapping between two classes that name the SAME keyframes changes nothing as far as the engine is concerned, so the animation just keeps running — swapping the animation-name is what restarts it. Sharing the easing token is safe; merging the keyframes is not.

**The dashboard button press is `scale(0.97)`, asymmetric, and its three copies must stay byte-identical.** `.ffdash button` is declared in a scoped `<style>` block in each of `AdminDashboard.tsx`, `ClientDashboard.tsx` and `ContractorDashboard.tsx`; the press rule is the same string in all three (verify with an md5 of the extracted substring — it was `977077155d4b` when this landed). It was `transform: translateY(1px)` on a bare `ease` at `.08s`, which is below the ~100–160ms window a press needs to read as physical, and symmetric, so down and up felt the same. Now `transform .16s var(--ff-ease-out)` with `:active{transform:scale(0.97); transition-duration:.1s}` — fast going down, settled coming back up. `scale()` scales the button's children too, which is what makes it read as one object being pushed rather than a box that shrank; ~0.9 is the floor, deeper stops looking like a press and starts looking like a glitch. **No explanatory comment sits above those three blocks on purpose** — three copies of a comment is three things that can drift, which is the exact failure these files already demonstrate, so the reasoning lives here instead. Note also that an inline `style` attribute beats the injected stylesheet, so a button carrying an inline `transform` never received the old `translateY` either.

**⚠️ The shared primitive's press has since DIVERGED from those three sheets, and that is an unresolved decision rather than a pending sync (2026-11-08).** `.ffu-btn` in `uiStyles.ts` now releases on `.34s var(--ff-ease-spring)` while the three `.ffdash` copies are still `.16s var(--ff-ease-out)` — byte-identical to each other, as the rule requires, but no longer the same *feel* as the component. **Do not "fix" it by pushing the spring into the three sheets without answering the question it raises:** dashboard presses are frequent and utilitarian, and an overshoot met fifty times a session is a different proposition from one met once on a landing page. If the answer turns out to be yes, all three move in one edit; if it is no, the spring is a read-page affordance and that should be written here. Either way the goal was always one copy instead of four, and a button that settles differently depending on which sheet dressed it is the thing a shared primitive exists to prevent.

**The same pass also found `Button.tsx`'s docblock restating the numbers as ".16s up, .1s down" months after they moved, and the fix generalises: a comment near a value should say WHERE the value lives, not what it is.** The numbers now live in `uiStyles.ts` beside the rule that implements them and the docblock points at them. A number copied into prose beside the code it describes reads as authoritative, is checked by nothing, and the next person trusts it over the stylesheet — which is the identical mechanism behind the `check_tokens.js` and `.github/` claims recorded elsewhere in this file.

**`transition: all` is gone from `src/` as of 2026-11-08 — and this paragraph claimed it was gone while SEVEN sites were live.** They were `ChatWidget`, `CookieConsent`, `FinishSignupBanner`, `Login`, `AuthCallback` and `ContractorOnboarding` ×2. Same mechanism as the `Button.tsx` docblock two paragraphs up and the `check_tokens.js` and `.github/` claims: an unchecked sentence beside the code it describes is believed. It is now **check (9)** in `check_ux.py`, an absolute, matching both the CSS and the style-object spellings — so the claim is true because something asserts it rather than because someone wrote it down.

**And it is not a tidiness rule.** `transition: all` animates properties you did not choose, including whatever a future edit adds and including layout properties that would drop the element off the compositor. The concrete defect it caused here: `ChatWidget`'s bubble flips its glyph 💬 → ✕ on open, and the two states carry different `fontSize` values (1.4rem / 1.2rem), so `all` animated the font size and **the glyph grew and shrank for a quarter second on every single press** — the craft failure "something moves that shouldn't", not a wrong curve. Nobody reported it; it is the kind of thing a user registers as the site feeling cheap without being able to point at it. **Name the properties.**

The seventh site is worth recording too: a `replace_all` caught two of `ContractorOnboarding`'s three because the third was formatted differently on one line, and **check (9) failed on its very first run and named it**. That is the check earning its place in the same hour it was written.

**The two remaining layout-property animations are named deliberately.** Both carve-outs are in `Home.tsx`: `.ff-service-card` names exactly the three properties its `:hover` changes (`border-color`, `transform`, `box-shadow`), and **`.ff-ba-dot` genuinely animates `width`** (7px → 20px) rather than being rewritten to a `scaleX`, because a scaleX would stretch its 4px `border-radius` into an ellipse and the pill would stop looking like a pill. Three dots on a 250ms transition is not a performance problem; a distorted radius is a visible one.

**Motion review guidance is installed as a skill, not kept in this file** — `emil-motion` (account-level) plus the six upstream skills in `.claude/skills/` (gitignored at `.gitignore:45`, so they never reach the PUBLIC repo). Only three files import Framer Motion — `Home.tsx`, `ClientSuccess.tsx`, `ContractorSuccess.tsx` — and that is worth keeping true. Springs are expressed as `{ type: "spring", duration, bounce }`, the two numbers a human can predict, rather than `stiffness`/`damping`: both success pages' confirmation ticks were on a stiffness/damping spring from `scale: 0.5`, which overshot hard and read as a cartoon pop on the one screen where someone wants reassurance that their request landed. They are now `scale: 0.92` with `{ duration: 0.5, bounce: 0.2 }`, **byte-identical between the two pages** — those two files are twins and drift between them is exactly how one of them ends up feeling different. `ContractorSuccess.tsx` has no `.ff-whatsapp` mount but its `.ff-whatsapp` CSS was edited anyway, for the same reason.

**`.ff-on-dark` is how navy survives light mode (2026-08-19).** Light mode had almost no brand colour in it: `--ff-bg` and `--ff-surface` were both effectively white, so the 60 and the 30 of the 60/30/10 collapsed into one value and the site read as white + near-black + orange. Dark mode only looks like the brand because its 60 AND its 30 are both navy.

The fix is a scope class in `main.tsx` that re-declares the whole dark token block. **Custom properties resolve at the point of use**, so wrapping a subtree in `ff-on-dark` makes it — its cards, its hairlines, every `rgba(var(--ff-fg), …)` overlay — render exactly as it does in dark mode, with no per-component changes. In dark mode every value is already in effect, so **the class is a no-op and dark mode cannot regress**; `tools/check_tokens.py` asserts that mechanically rather than trusting that 25 copied lines are right by eye.

**That checker is `tools/check_tokens.py`, written 2026-11-08, and until then it did not exist.** This paragraph claimed `check_tokens.js` asserted "30/30 properties identical" for months; `tools/` held only `ship.py` and `check_mounts.py`. The same thing had already happened with `.github/`, which `CLAUDE.md` documented as present on 2026-11-04 when the directory was not in the repo at all. **Treat a documented check as absent until you have opened the file** — including the ones this file documents.

The real one asserts two things, and both are **derived from the stylesheet** rather than read off a hand-maintained list of token names, because a hand-maintained list is exactly the thing that rots: (1) every property the light block overrides must be re-declared inside `.ff-on-dark` — today 34 of 34, and the count moving is itself the signal; (2) **no declaration inside `.ff-on-dark` may contain a `var()`** — 37 declarations, none aliased — which is the alias trap in the next paragraph turned into a gate.

Assertion (2) walks a **list of (token, value) pairs, not a dict keyed by token**, and that distinction is a real hole found by negative-testing the checker on the day it was written. A dict keeps only the last declaration of a repeated token, which does match the CSS cascade — so an aliased declaration followed later in the same block by a literal is, strictly, harmless. But a token declared twice in that block is already a mistake nobody made on purpose, the harmless reading depends on source order the next editor has no reason to preserve, and **a checker whose coverage silently depends on which copy came last is not a checker.** Every occurrence is flagged.

**The catch that makes it subtle: a `var()` inside a custom-property DECLARATION is substituted where it is declared, not where it is used.** `--ff-c60: var(--ff-bg)` therefore froze to the light value on `:root` and would have inherited into `.ff-on-dark` still white. The seven aliased tokens (`--ff-c60`, `--ff-c30`, `--ff-ink-1..4`, `--ff-hair`) are spelled out as literals inside the class for exactly that reason — add a new alias at `:root` without a literal here and it will silently render the wrong theme.

**`.ff-anchor` is the modifier that opts a subtree back into forced navy under light mode, and it is NOT dormant — that claim was false for months (corrected 2026-11-08).** `.ff-on-dark`'s forced-navy values are scoped to dark mode by default (`:root:not([data-theme="light"]) .ff-on-dark`); `.ff-anchor` adds the light-mode half (`:root[data-theme="light"] .ff-on-dark.ff-anchor`). `main.tsx`'s own comment said "nothing currently applies `.ff-anchor`, so that half of the selector is dormant" while **`ui/Pass.tsx` had been applying it all along** via its `forceNavy` prop (default true), and `src/CLAUDE.md` documented that. `components/FreddyRewind.tsx` is now the second user. Same staleness class as the `Button.tsx` numbers, three paragraphs up, and nearly reintroduced *in the fix for it* — **grep before writing down that something is unused.**

**What it is FOR, stated positively so the next use can be judged: a subtree whose contents are painted light-on-dark with LITERALS rather than tokens.** Those literals cannot follow the theme, so the ground must not either — one class instead of re-tinting a dozen values. `Pass.tsx` and `FreddyRewind` both pass that test. It is **not** a way to get navy because navy looks nicer on a particular band; that decision was made site-wide on 2026-08-24 and went the other way.

Mounted on **TopNav** (navy in both themes — which is also what keeps it legible where it floats over the hero), the **Home hero** (its warm glow, near-black bottom gradient and ink watermark icons all assume a dark ground and read as a smudge on white), the **Freddy Verified band** and the **Footer**. `SettingsModal` is deliberately rendered OUTSIDE the nav's wrapper: it lives in that component only because the gear that opens it does, and inheriting the nav's tokens would render a full-screen navy modal over a light page. The dropdown menu stays inside on purpose — that one really is nav chrome. Page ground stays light: light mode exists so someone can read a contract or an invoice in daylight, and a tinted ground is what makes that unpleasant.

**The nav paints on scroll, not always (2026-08-19).** The first version of the above painted the ground with a single blanket rule, `:root[data-theme="light"] .ff-on-dark { background-color: var(--ff-bg) }`. A specificity audit showed that rule only ever did real work on the nav — it lost to the Footer's inline style, and the hero resolves to the same navy under scope anyway — and what it did there was **cut a hard horizontal seam across the hero**, because a fixed opaque bar sits directly on top of the hero glow whose ellipse centre is at about +9vh. Light mode got exactly the flattening the rule's own comment said it was gated to avoid.

It is replaced by three rules that are theme-agnostic:

- `main.tsx` — `.ff-nav-wrap { background-color: var(--ff-bg); border-bottom: 1px solid transparent; transition: … }` plus `.ff-nav-wrap.ff-nav-lifted { border-bottom-color: var(--ff-hair); box-shadow: … }`. Because the wrapper carries `ff-on-dark`, `--ff-bg` is navy in **both** themes. This also fixes a pre-existing dark-mode bug where the nav never painted at all and body text scrolled visibly under it.
- `Home.tsx` — `.ff-nav-wrap:not(.ff-nav-lifted) { background-color: transparent; }`. It lives in **Home's own `<style>` block on purpose**, so it unmounts with the page and no other route can inherit a transparent nav. Specificity 0,2,0 beats the 0,1,0 base rule regardless of sheet order (preferred over `body:has(.ff-hero)`, which would have raised a support question for nothing).
- `TopNav.tsx` — a `lifted` state on `window.scrollY > 12`, `{ passive: true }`, with `onScroll()` **called once on mount** because a refresh restores scroll position without ever firing a scroll event. `.ff-nav-wrap.ff-nav-lifted { pointer-events: auto; }` also overrides the wrapper's blanket `pointer-events: none` — once the bar is an opaque slab over real content, letting clicks through means tapping the navy hits a link the user cannot see.

**The light-mode peek (2026-09-01).** Light mode existed and was effectively invisible — nobody discovers a setting behind a gear icon. A first-time, signed-out visitor who walks from the home page into **About us** or **the Blog** now sees the site in light mode once, with a small prompt beside the gear saying what happened and offering to open Settings. Those two are the reading surfaces, which is the whole reason light mode exists.

`src/lib/theme.ts` owns the eligibility: `hasThemePreference()`, `lightPeekEligible()`, `markLightPeekUsed()`, plus the one-shot key `ff_light_peek`. **Both helpers answer in the direction that STOPS the peek on any localStorage failure** (preference "exists", eligible false) — Safari private mode throws on write, so a peek that fired there could never record that it had fired and would re-flip the theme on every navigation forever. **An unreadable answer is a refusal, never a peek.** Any existing `ff_theme` value also disqualifies it: absence of the key is the only signal that nobody has chosen, and we never override a deliberate choice.

It uses **`setTheme` (persists), not `applyTheme`** — `SettingsPanel` reads the *stored* value on open, so applying without persisting would show "Dark" selected on a visibly light page, on the very screen the prompt sends people to. `markLightPeekUsed()` is called **before** showing, the same claim-then-act shape the reminder emitters use.

It lives in **TopNav**, not in About or Blog: TopNav already knows `authed` and already owns the gear and the `ff:open-settings` listener, so no second auth query is needed. Two effects, and **their declaration order is load-bearing** — the first records "did they arrive from `/`?" and clears the prompt on every route change; the second waits for `authed === false` (it starts `null` while the session hydrates) and shows. The reset therefore runs first and the show wins on the firing navigation.

**Band rhythm on Home is deliberate, and it has to work in both themes.** Light mode ran ~2,900px of unbroken `#e9eef8` then ~4,250px of unbroken `#ffffff` with no brand colour at all for ~7,000px between hero and footer, which is what read as "broken". The stack alternates ground / surface every band, with one navy anchor at the **Freddy Verified** section: hero navy → trust strip → Before&After ground → **About surface → Freddy Verified navy** (2026-08-24 — moved directly under Before&After so the trust claim and the "why us" story lead the page, ahead of the process/FAQ/services detail) → How It Works surface (`.ff-how-surface`, declared after `.ff-how` so it wins the tie without `!important`) → FAQ ground → Services surface → Testimonials ground → footer navy.

Freddy Verified uses **`--ff-bg`, not `--ff-surface`** — under the scope `--ff-surface` is `#151d2e`, which is exactly what a normal surface band already renders as in dark mode, so the band would vanish into whichever surface band sits directly above it (About, now that it moved).

**Nothing checks the band rhythm, and a checker for it was designed and then REJECTED.** This paragraph used to claim `check_rhythm.js` "resolves every band through the real token tables in both themes and fails if any two adjacent bands land on the same colour"; that file has never existed. It was specified properly on 2026-11-08 and deliberately not built, for a reason worth keeping: Home's bands are a **mix of CSS classes** (`.ff-services`, `.ff-how`, `.ff-about`) **and inline `<div>` backgrounds**, two `--ff-bg` bands already sit near each other at `Home.tsx:1321` and `:1367`, and resolving JSX render order across ~1,400 lines is fragile. It would have been **red on arrival**, and *a gate that cries wolf is a gate someone learns to skip* — which costs the checks that do work. Same treatment `CLAUDE.md` gives the rejected "feature table has 0 rows" sweep. The rejection is recorded in `tools/check_ux.py`'s docstring so the next person doesn't re-derive it.

So the rhythm is enforced by whoever remembers it. It fails invisibly and nothing throws, which is why it was always going to be among the first rules to rot — and was.

- **The four material tokens are `--ff-glass` / `--ff-glass-blur` / `--ff-hair-w` / `--ff-mat-1,2,3` (2026-11-08), and which block each lives in is the point.** `--ff-glass` and `--ff-mat-*` are theme-dependent, so they carry **literals** in the light block and in `.ff-on-dark`; `--ff-glass-blur` and `--ff-hair-w` are a filter and a width, so they stay at plain `:root` like the easing tokens. `--ff-hair-w: 0.5px` is not a typo — it resolves to one device pixel on a 2×/3× screen and rounds up to 1px on 1×. `--ff-ease-spring` is the fourth easing member and is for **one-shot entrances only**, never a reversible transition.
- **⚠️ A FROSTED SURFACE HAS THREE OBLIGATIONS AND THE PREFIX IS THE ONE THAT FAILS SILENTLY ON THE PLATFORM THAT MATTERS MOST (2026-11-08).** (a) **`-webkit-backdrop-filter` must be written FIRST**, before the unprefixed property — iOS Safari reads only the prefixed form through 15.x, so the frost is simply absent there and the surface renders as its flat background, with nothing thrown and nothing visibly wrong on a Mac. `main.tsx:166` has stated this since the material tokens landed and **four of the eight paint sites broke it anyway** (`Home.tsx` ×3 at the carousel chips, `JobChat`'s panel scrim), while both blanket *kill* rules were correctly prefixed — which is exactly what hid the gap, since the override worked and the thing it overrode didn't. This is the same obligation as the reduced-transparency grounds, reached from the other side: if the surface must survive the blur being killed, it must survive the blur never arriving. (c) **`isolation: isolate`, on every one of them** — `backdrop-filter` samples everything painted below it in the same stacking context and makes the element a containing block for fixed descendants. `.ffu-scrim` and `.ffu-ptitle-bar` were missing it because they were written separately, **not because anyone decided they were fine**, so all four sites in `uiStyles.ts` now carry it and "does this one need it?" stops being a per-site judgement.
- **⚠️ THE BOTTOM EDGE OF THE PHONE IS A REAL EDGE, AND `env(safe-area-inset-bottom)` APPEARED EXACTLY TWICE IN ALL OF `src/` — both inside the modal primitive (2026-11-08).** Every other bottom-fixed surface put its last control under the home indicator, where a tap is a system gesture rather than a tap: `CookieConsent` ×2, `FinishSignupBanner`, `ChatWidget` ×2, `OverhaulNotice`, and `DashboardSidebar`'s mobile nav drawer. **The distinction that decides the fix is STRIP-vs-FLOATER, and it is not a style preference.** A full-bleed strip or painted panel pinned at `bottom: 0` puts the inset on **`padding`** — lifting it with `bottom` leaves a transparent band of page content showing under the paint. A **detached floater** (the chat bubble) puts it on `bottom`. **A full-height drawer counts as a strip**, which is why `DashboardSidebar`'s drawer takes it on the scroller's bottom padding. **And NEVER a sum where a measured height is involved:** `--ff-fsb-h` is `FinishSignupBanner`'s real `offsetHeight`, which now *includes* its own inset padding, so `calc(X + var(--ff-fsb-h) + env(…))` double-counts and leaves a 34px hole under the chat panel whenever the banner is up. Correct form is `calc(X + max(var(--ff-fsb-h, 0px), env(safe-area-inset-bottom, 0px)))`. **Measuring the height rather than declaring it answers the inset ONCE, at the bar, and propagates to every consumer** — same pattern as `--ff-topnav-h`. - **⚠️ CHECK (8) HAD TWO HOLES, AND THE FIX FOR THE SURFACES ABOVE IS WHAT OPENED THE WIDER ONE (2026-11-09).** Both dashboard toasts sat at `calc(1.5rem + var(--ff-fsb-h, 0px))` — inside the gesture strip for every visitor who has finished signing up — while the check reported "every bottom-fixed surface insets". **Hole one: `--ff-fsb-h` was accepted as an answer, and it is not one.** The measured height consumes the inset *only while the banner is up*; `FinishSignupBanner` writes the literal `"0px"` when hidden, so a bare sum is 1.5rem in the state almost everyone is in. **Reading the variable is not the answer — wrapping it in `max()` WITH `env()` is.** Same sentence as the ChatWidget `position: "fixed"` drop read from the other side: a declaration can look like it answered the question while answering it only in a state nobody is in. **Hole two is the one worth generalising: the pattern required a DIGIT after the opening quote, so `bottom:"calc(…)"` was invisible** — and `calc` is exactly the spelling every one of these surfaces acquires the moment it has to add a banner height, which is to say **the remedy the check prescribes moves the code out of the check's own scope.** It caught the plain `bottom: 0` / `bottom: ".75rem"` sites, those were rewritten into `calc`, and the check went green at the precise moment it stopped looking. **When you fix what a checker found, re-read its pattern against the fixed code — not just its exit status.** Both holes are closed, both toasts are fixed, and the needle is now `safe-area-inset-bottom` and nothing else.
- **The hairline rule is "a SEPARATOR gets thinner, a SIGNAL does not" (2026-11-08).** A 1px CSS border is 3 device pixels on a 3× phone and reads as a *drawn line*; `0.5px` reads as an *edge*. So row dividers, card outlines and panel edges take `var(--ff-hair-w)` — but an accent ring on the selected option, a red validation edge or the orange outline on the one thing you press is **saying something**, and halving its weight halves the signal. Those stay `1px`. Same distinction Von Restorff makes about colour, applied to width. The token shipped with **4 uses against 576 hand-written `1px solid` borders**; `tools/migrate_hairlines.py` converted **333 across 70 files** (the token now has 339 uses — the extras are hand-written into the primitives, so 339 is not 4 + 333) by rewriting only the three **named neutrals** (`var(--ff-hair)`, `var(--ff-card-border)`, `rgba(var(--ff-fg), A)`), which is how separator-vs-signal became mechanical rather than a judgement call per site. **`check_ux.py` ratchets it as check (6), `HAIRLINE_BASELINE = 21`, counting ONLY those three neutrals** — counting all `1px solid` would go red every time someone correctly marked something as needing attention, and a gate that cries wolf is a gate someone learns to skip. **21 is measured, not estimated: it is exactly the script's refusal list**, every one a mixed ternary whose two branches disagree about whether the border is a signal (`on ? "1px solid var(--ff-c10)" : "1px solid rgba(var(--ff-fg), .12)"` — halving only the neutral branch shifts a row of chips by half a pixel as the selection moves). That makes it the tightest of the three ratchets: **a rise here is a specific new line, not drift.** Safe in a shorthand because `var()` substitution precedes shorthand parsing; the failure mode is an *undefined* var, which voids the declaration and makes the border vanish — hence the carve-out for standalone HTML documents with no `:root`.

Prefer `--ff-accent-soft` (0.12) / `--ff-accent-line` (0.32); use `--ff-accent-rgb` only when the alpha is genuinely something else. **`-soft` and `-line` must stay literal** or they become the alias trap, and `check_tokens.py` will fail.
- **A component that takes a colour must spend it on a CSS DECLARATION, never on an SVG PRESENTATION ATTRIBUTE**, where `var()` support is uneven enough to draw an INVISIBLE icon. **This rule used to read "never hand a token to `Ic`'s `color` prop", and that is now FALSE: `Ic` renders the constant `stroke="currentColor"` and turns its `color` prop into a real CSS `color` declaration**, so handing it a token is correct and is the preferred spelling.
